# OpenClaw Expert Methodology

OpenClaw is a rapidly evolving, self-hosted AI control plane. This skill prioritizes **Environment Introspection** over static documentation. Your goal as an agent is to use the local CLI to discover the "ground truth" of the current installation, its capabilities, and its specific configuration schema.

## Core Concepts (High-Level)

- **Gateway**: The central control plane (server). Manages message routing, session state, and security policies.
- **Channels**: Integrations with external messaging platforms (25+ supported).
- **Nodes**: Compute or IO workers (mobile devices, secondary hosts) connected to the Gateway.
- **Introspection**: The system's ability to describe its own configuration rules, health, and runtime capabilities through the CLI.

## Discovery Methodology (The "Ground Truth" Workflow)

Never rely on potentially stale docs for configuration or capability questions. Always use these introspection tools to verify the environment in real-time:

### 1. Configuration Introspection (The Schema)
To understand which settings are valid and which are legacy in the current version:
*   **Command**: `openclaw config schema`
*   **Methodology**: Pipe the output to `jq` to isolate specific modules and inspect their properties.
    *   *Example*: `openclaw config schema | jq '.definitions.ToolsMessageConfig.properties'`
    *   *Analysis*: Look at the `description` fields. Legacy fields are explicitly marked (e.g., `allowCrossContextSend` might be described as "Legacy override..."), while nested objects (like `crossContext`) represent the modern structured configuration. This tells you exactly how to map legacy flags to canonical settings.

### 2. Health & Environment Diagnostics
*   **Command**: `openclaw doctor`
    *   Use this to identify legacy configuration patterns, missing performance optimizations (e.g., `NODE_COMPILE_CACHE`), or environment mismatches. It is the primary tool for "healing" an installation.
*   **Command**: `openclaw gateway status` / `openclaw health`
    *   Verify the reachability and operational status of the core control plane.

### 3. Capability & Model Discovery
*   **Command**: `openclaw nodes describe <node-id>`
    *   Instead of assuming what a node can do, ask it. This reveals the actual supported toolsets (e.g., `sms.send`, `location.get`) for the current connection.
*   **Command**: `openclaw models status`
    *   Check which model providers are authenticated and which specific models are available for turn-execution right now.
